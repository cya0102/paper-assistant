# Paper Agent 使用说明

本文档适用于当前 Research Graph Foundation 修订版（`paper-agent 0.6.0`）。

当前版本已经形成可运行的本地论文 Agent 后端：除 PDF 导入、结构恢复、分层索引和混合检索外，还提供可恢复 Agent Loop、`search_knowledge`/`read_paper` Tool、Query Rewrite、Neighbor Expansion、Evidence Judge、引用校验、Redis 短期状态、PostgreSQL Interaction Memory，以及 Evidence-first Research Graph 和结构化多论文比较。

默认摄取和检索仍可完全离线运行。只有执行 `paper-agent ask` 或显式切换 OpenAI Embedding 时才需要模型 API Key。

## 开发阶段总览

当前项目已经完成 Phase 1A、Phase 1B、Phase 1C、Phase 2A、Phase 3，以及 Research Graph Foundation 的第一条可验收纵切。

| 阶段 | 核心目标 | 阶段完成后的能力 |
|---|---|---|
| Phase 1A | 建立领域模型、数据库和增量摄取骨架 | 可以发现 PDF、计算文件 Hash、去重并记录摄取状态 |
| Phase 1B | 接入真实 PDF Parser、Metadata 和 Paper/Version Identity | 可以把真实 PDF 转换为持久化的 Canonical Parsed Document |
| Phase 1C | 恢复论文结构并生成语义 Chunk | 可以生成 Section-aware、版本化且完整可追溯的结构化 Chunk |
| Phase 2A | 建立分层索引和混合检索 | 可以使用 Metadata、Dense、BM25 和 Reranker 检索可追溯 Evidence |
| Phase 3 | 建立 Agent Runtime、阅读工具、上下文和用户记忆 | 可以由模型选择 Search/Read，并生成经引用校验的答案和可恢复会话 |
| Research Graph Foundation | 建立 Profile/Claim/Entity/Relation/Evidence 与证据化比较 | 可以离线提取结构化论文画像，并拒绝无证据比较项 |

### Phase 1A：摄取基础设施

Phase 1A 的目标是建立确定性、可测试、可扩展的论文导入底座。该阶段不负责深入理解 PDF 内容，而是先解决文件发现、身份分层、数据库持久化和流水线可靠性。

该阶段实现了：

- 建立 `Project`、`FileLocation`、`PaperFile`、`Paper`、`PaperVersion`、`IngestionRun` 和 `IngestionItem` 等核心 Domain Model。
- 将物理文件、逻辑论文和论文版本分开建模：一个 Paper 可以有多个 Version，一个 Version 可以对应多个文件位置。
- 建立 PostgreSQL 初始 Schema 和 Alembic `0001_phase1` Migration。
- 实现 Repository 与 Unit of Work 接口，让 Domain/Ingestion 层不直接依赖 PostgreSQL。
- 实现项目范围内的递归 PDF Directory Scanner。
- 扫描时校验路径，拒绝读取项目根目录之外的文件。
- 使用流式读取计算文件 SHA-256，适用于大文件，不需要一次把整个 PDF 读入内存。
- 检测 Hash 计算期间文件是否发生变化，并返回稳定错误。
- 根据 `project_id + file_hash` 对完全相同的 PDF 二进制进行去重。
- 支持同一文件出现在多个项目相对路径，以及改名后复用已有 File 记录。
- 定义版本化 Canonical Parsed Document 接口，包括 Page、Block、BBox、Reading Order 和 Parser Provenance。
- 建立 Ingestion Pipeline Skeleton，按文件隔离事务与失败；单篇失败不会中断整批导入。
- 保存 Ingestion Run、每个文件的 Stage、Disposition、错误码和计数。
- 为 `discovered`、`identity_resolved`、`parsing`、`parsed`、`failed` 等状态建立统一枚举。

Phase 1A 完成后，项目已经具备可靠的“扫描、Hash、去重、记录状态”能力，但还没有接入真正的 PDF 内容解析和论文语义身份判断。

### Phase 1B：真实 PDF 解析与论文身份

Phase 1B 的目标是把 Phase 1A 的摄取骨架扩展成可以处理真实 PDF 的增量导入工具，并生成稳定的中间表示。

该阶段实现了：

- 接入 PyMuPDF 作为默认 PDF Parser。
- 接入 Poppler CLI 作为后备 Parser。
- 从真实 PDF 提取页面尺寸、文本 Block、BBox、Reading Order 和基础 Heading/Paragraph 类型。
- 对加密 PDF、损坏 PDF、空 PDF 和 Parser 不可用返回稳定错误码。
- 提取 Title、Authors、Subject、Keywords、DOI、arXiv ID、年份和 Page Count 等 Metadata。
- 保存 Metadata 的来源、证据和置信度。
- 规范化 Title、Authors、DOI、arXiv ID、Unicode、空白和断行连字符。
- 从规范化正文计算 Content Fingerprint。
- Content Fingerprint 会尽量忽略重复页眉、页脚和页码。
- 分层使用 Content Hash、DOI、arXiv ID、Normalized Title 与 Authors 解析 Paper/Version Identity。
- 相同正文复用已有 PaperVersion；相同 DOI/arXiv 但正文不同则创建同一 Paper 下的新 Version。
- 避免仅凭模糊标题自动合并论文，降低错误去重风险。
- 把 Canonical Parsed Document 保存为 `document.json` 和 `document.md`。
- 增加 Local Parsed Document Store，并保留 Parser 名称、Parser Version 和 Canonical Schema Version。
- 实现 `force_reindex`、Parser Version 失效和 Canonical Schema Version 失效机制。
- Parser 或 Schema 变化时重新解析；没有变化时复用已有解析结果。
- 全项目扫描时把已经移除的路径标记为 `missing`，但不删除论文历史数据。
- PostgreSQL 使用 `ON CONFLICT` 处理并发插入相同 SHA-256 File 的情况。
- 增加 Alembic `0002_phase1b` Migration，保存 Content Hash、Page Count 和规范化 Metadata。
- 增加稳定项目身份文件 `.paper-agent/project.json`。
- 增加 `paper-agent init`、`ingest`、`status` 和 `db-upgrade` CLI 命令。
- 引入 `uv.lock`，固定可复现的 Python 依赖环境。

Phase 1B 完成后，项目可以实际导入真实 PDF，建立 File/Paper/Version 身份并生成 Canonical Parsed Document；此时它是可运行的论文导入工具，但尚未产生适合检索的 Section 和 Chunk。

### Phase 1C：论文结构恢复与语义分块

Phase 1C 的目标是从 Canonical Parsed Document 构建版本化的论文结构和检索语义单元，并保证所有派生数据可以独立恢复与重建。

该阶段实现了：

- 新增 `Section`、`StructuredDocument`、`Element`、`SemanticGroup`、`Chunk` 和 `DerivedDataState` Domain Model。
- 建立 Section Tree Builder，恢复显式 Heading Level、数字编号、罗马数字、字母编号和常见论文章节标题。
- 修正不合理的 Heading 层级跳跃，并生成 `parent_section_id`、`level`、`section_order` 和 `section_path`。
- 将标题前内容放入合成的 `Front Matter` Section。
- 按 Canonical Reading Order 将每个 Block 唯一归属到一个 Section。
- 每个 Section 保存页范围、来源 Heading Block 和完整 `source_block_ids`。
- 建立 Figure、Table、Equation 和 Algorithm 四类基础 Element。
- Element 保存所属 Paper/Version/Section、Label、Caption/Content、Page、BBox 和来源 Block。
- 建立普通 Semantic Block 和 `element_dependency` Dependency Group。
- 尽量将公式前定义、公式、公式后变量解释组合为不可随意拆分的语义单元。
- 尽量将 Figure/Table/Algorithm、Caption 和邻近引用正文保持在同一 Dependency Group。
- 建立 Section-aware Semantic Chunker，以 Paper 和 Section 为硬边界，不跨 Section 合并内容。
- 默认目标长度约 600 tokens、硬上限约 800 tokens，并支持配置。
- 普通超长文本可以按句子和 token 降级拆分；中文无空格长文本也能正确处理。
- Dependency Group 优先保持语义原子性，即使特殊情况下超过普通 Chunk 硬上限也不会强制拆散。
- 使用稳定 UUID 生成 Section、Element、Semantic Group 和 Chunk ID，使相同输入可以得到确定性结果。
- 每个 Chunk 保留 Paper、Version、Section、Page、Semantic Group、Block 和 Element 的完整溯源。
- 分别记录 Structure Version 与 Chunking Version。
- 只有 Chunking Version 变化时只重建 Chunk；Structure Version 变化时复用 Canonical Document 并重建结构及下游数据。
- Parser 或 Canonical Schema Version 变化时重新解析并重建全部下游派生数据。
- 使用事务内 Replace 语义重建派生数据，避免同一 PaperVersion 混入不同算法版本的结果。
- 增加 Alembic `0003_phase1c` Migration，创建 `sections`、`elements`、`semantic_groups`、`chunks` 和 `derived_data_states`。
- 增加派生数据 PostgreSQL Repository，支持结构和 Chunk 的保存、加载、替换及恢复。
- 扩展 CLI `status`，显示 Section、Element、Semantic Group 和 Chunk 数量。
- 在真实 PostgreSQL 17.10 环境完成 `0001 → 0002 → 0003` Migration、`0003 → 0002 → 0003` 往返验证和 Repository 集成测试。

Phase 1C 完成后，默认 Ingestion Pipeline 会执行到 `chunked`。项目现在可以作为论文检索系统的结构化预处理层，但还不能直接执行自然语言检索、RAG 问答或 Agent 对话。

### Phase 2A：分层索引与混合检索

Phase 2A 的目标是把 Phase 1C 的结构化 Chunk 转换为可增量重建的 Paper/Section/Chunk 三层索引，并提供低噪音、可拒答、完整可追溯的内部检索服务。

该阶段实现了：

- 定义可替换的 `EmbeddingProvider`，支持真正的批量 Embedding 调用。
- 提供离线确定性的 256 维 Hashing Embedding 默认实现，无需下载模型或访问网络。
- 保存 Embedding Provider、Model、Version 和 Dimension。
- 为 Paper、Section 和 Chunk 分别生成向量表示。
- Paper 表示包含 Title、Aliases、Authors、Venue、Abstract、Section 路径和有限正文摘要。
- Section 表示包含 Section Path 和所属 Chunk 内容。
- Chunk 表示包含 Section Path 和 Chunk Text。
- 新增 pgvector `vector(256)` Schema 和 Paper/Section/Chunk HNSW Cosine Index。
- 新增 PostgreSQL `tsvector` 生成列和 GIN 全文索引。
- 使用 PostgreSQL FTS 扩大 Sparse Candidate Recall，并使用标准 BM25 公式重评分。
- 支持按 Project、Paper、Version、Section 限定检索范围。
- 支持 Year、Venue、Author 和 Chunk Type Metadata Filter。
- 实现 Paper → Section → Chunk 分层召回，避免直接把全库 Chunk Top-K 交给下游。
- 在 Chunk 层融合 Dense Vector Candidate 与 Sparse BM25 Candidate。
- 定义可替换 `Reranker` 接口，并提供离线 Lexical Hybrid Reranker。
- 实现可配置 Threshold，所有候选低于阈值时返回明确的 `no_evidence`。
- 实现近重复 Evidence 去重与按 Paper 配额的基础 Diversity Selection。
- Evidence 保留 Paper、Version、Paper Title、Section、Page、Chunk、Element 和各阶段 Score。
- 实现内部 `SearchKnowledgeService.search_knowledge()` 服务。
- 将 Embedding/Indexing 接入默认 Ingestion Pipeline，成功状态从 `chunked` 延伸到 `indexed`。
- 只改变 Embedding/Index Version 时，仅重建索引，不重跑 Parse、Structure 或 Chunk。
- Structure/Chunk 被替换时，在同一事务中失效旧 Index State 和三层向量，防止检索到陈旧数据。
- 增加 Alembic `0004_phase2a` Migration 和真实 PostgreSQL/pgvector 端到端集成测试。

Phase 2A 完成后，项目已经具备检索后端能力。`search_knowledge` 当前是内部 Python Service，还不是 LLM Tool，也不会自动生成最终自然语言答案。

### Phase 3：Agent Runtime、阅读与记忆

Phase 3 把 Phase 2A 的检索后端接入可恢复的模型工具循环，并补齐精确阅读、上下文控制和用户记忆。

该阶段实现了：

- 自研可恢复 `AgentRuntime`，不把核心状态绑定到 LangChain/LangGraph。
- 在模型响应、待执行 Tool 和每个 Tool Result 后保存 Checkpoint；进程中断后只继续未完成调用。
- 最小 `ToolRegistry`、JSON Schema `ToolContract`、未知 Tool 拒绝和错误结果回传。
- 将内部 `search_knowledge` 封装为 LLM Tool，输入可限定 Paper、Section、Chunk Type 和 Evidence 数量。
- 新增 `read_paper`，支持按 Section、Page Range、Element ID 和 Figure/Table/Equation/Algorithm 类型读取，并可包含相邻 Chunk；每个阅读段落与 Element 返回 `[P{数字}]` 引用编号（分别由 Chunk/Element ID 稳定派生），并统一汇入顶层 `evidence`，与检索证据的 `[E{数字}]` 分开校验。
- 增加保守 Query Rewrite 与 2～4 条 Multi-query 执行、跨 Query Chunk 去重和最高分融合。
- 增加同一 Version/Section 内的 Chunk Neighbor Expansion，不盲目扩大全局 Top-K。
- 增加可替换 `EvidenceJudge`，默认使用离线校准的词法判断器过滤无关证据。
- 增加 `ContextBuilder`，按 Token Budget、每篇 Paper 上限和轮询配额平衡多论文 Evidence。
- 为 Tool Evidence 分配稳定的 `[E{数字}]` 引用编号（由证据 ID 稳定派生，示例 `[E62497060534405]`）；最终答案出现未知引用或有证据却无引用时拒绝完成。
- 增加 OpenAI Responses API 模型适配器，以 `previous_response_id + call_id` 继续 Tool Loop。
- 增加 Redis Agent Checkpoint 和 Session State，保存近期消息、当前 Paper、Active Chunk 和最近 Tool Result，并设置 TTL。
- 增加 PostgreSQL `interactions`、`notes`、`user_preferences` 表与 Repository。
- Agent 成功回答后自动写入 Interaction Memory 和 Redis Session；后续同一 Session 会回填近期消息以处理“刚才那篇论文”等指代。
- 增加 OpenAI 批量 Embedding Provider，保持当前 Schema 所需的 256 维输出。
- 增加可选 Sentence Transformers Cross-Encoder Reranker，依赖和模型采用按需安装/下载。
- 增加 `search`、`read` 和 `ask` CLI。
- 增加 Alembic `0005_phase3` Migration，以及 Agent/Search/Read/Memory、Redis TTL 和真实 PostgreSQL 端到端测试。
- 修复 Parser/Canonical Schema 变化后旧 Structure/Chunk 被错误复用的问题：`derived_data_states.document_hash` 现在绑定最新 Parsed Document；存量 `NULL` 会在下次 ingest 时安全重建一次。
- 修复 Structure 重建时绑定 Section 的 Note 被级联删除的问题：Section 外键现在使用 `ON DELETE SET NULL`，Note 保留但解除失效的 Section 关联。

Phase 3 完成后，项目已经可以作为单机论文问答 Agent 后端使用。默认离线检索质量仍是基线级；要生成自然语言答案需要配置模型 API Key，神经 Embedding/Cross-Encoder 可按需启用。

### Research Graph Foundation：结构化论文理解与比较

本纵切在现有 Chunk/Evidence 之上建立可查询的研究知识层：

- `PaperProfile` 保存一次特定 PaperVersion 的版本化提取结果；稳定字段保存为 `paper_profile_fields` 行，而不是单一 JSON Blob。
- Profile 字段覆盖 research problem、motivation、hypotheses、contributions、method、assumptions、datasets、metrics、baselines、experimental settings、results、limitations、failure cases 和 future work。
- `Claim` 保存独立主张、归一化文本、极性、置信度、提取版本、人工 Review 和 Entailment 状态。
- `ResearchEntity` 与独立 Alias 表统一 task/problem/method/component/mechanism/dataset/metric/baseline/concept/domain。
- `PaperRelation` 支持 Paper/Entity 端点和 cites/extends/improves/uses/evaluates/supports/contradicts/analogous 等关系。
- `EvidenceLink` 保存 Project、Paper、Version、Section、Chunk、可选 Element、页面、Source Block、证据文本快照和事实/总结/推断类型。
- 默认 `RuleBasedPaperProfileExtractor` 和 `LexicalEntailmentJudge` 完全离线；在线 LLM 只能通过同一 Protocol 接入。
- active/superseded 语义保留旧派生结果；相同生成版本重复执行使用稳定 ID 和数据库唯一约束去重。
- `EvidenceBackedComparisonService` 只读取已存 Profile/Claim。有内容的 Cell 必须携带 EvidenceLink；缺失信息返回 `insufficient_evidence`。
- 新增 Agent `compare_papers` Tool，以及 `profile-extract`、`compare` CLI。

完整的 Phase A～F 计划见 `docs/research-graph-roadmap.md`。当前没有用空表或空 Provider 冒充 Literature Review、Cross-domain Inspiration、External Discovery 或 Production 能力。

### 当前阶段边界与下一阶段

截至当前 Research Graph Foundation，完整处理链为：

```text
PDF 目录
→ Directory Scan
→ SHA-256 / Content Fingerprint 去重
→ File / Paper / Version Identity
→ PDF Parsing
→ Canonical Parsed Document
→ Section Tree / Element / Dependency Group
→ Section-aware Semantic Chunk
→ Paper / Section / Chunk Batch Embedding
→ pgvector + PostgreSQL FTS/BM25 Index
→ Metadata Scope + Hierarchical Hybrid Retrieval
→ Rerank + Threshold + Dedup
→ Traceable Evidence / no_evidence
→ Agent Tool Loop（Search / Read / Compare）
→ Budgeted Context + Citation Validation
→ Final Answer
→ Redis Session + PostgreSQL Interaction Memory
→ PaperProfile / Claim / Entity / Relation / EvidenceLink
→ Evidence-backed Comparison / insufficient_evidence
→ PostgreSQL 可追溯持久化
```

下一阶段先持久化 ComparisonTask/Cell/Artifact 和人工修订，再以它为 Evidence Matrix 底座进入 Literature Review Workflow。服务化与质量工程按路线图后续推进。

## 1. 当前支持的功能

- 递归扫描项目中的 PDF。
- 流式计算文件 SHA-256。
- 相同 PDF 改名后复用已有记录，不重复解析。
- 根据规范化正文生成 Content Fingerprint。
- 不同 PDF 二进制但正文相同时复用已有 PaperVersion。
- 提取标题、作者、DOI、arXiv ID、年份、页数等基础元数据。
- 使用 DOI、arXiv ID、标题、作者和正文 Hash 判断 Paper/Version 身份。
- 使用 PyMuPDF 解析真实 PDF。
- PyMuPDF 不可用时可以使用 Poppler 后备解析器。
- 生成 `document.json` 和 `document.md`。
- 支持 `force_reindex` 强制重新解析。
- Parser 或 Canonical Document Schema 版本变化时重新解析。
- 一篇 PDF 失败不会中断其他 PDF。
- 全项目扫描时将已经移走或删除的路径标记为 `missing`。
- 恢复标题层级并构建版本化 Section Tree。
- 将每个 Canonical Block 唯一归属到一个 Section。
- 建立 Figure、Table、Equation、Algorithm 基础 Element。
- 将公式/图表及其说明上下文组合为 Dependency Group。
- 在 Section 边界内进行 Semantic Chunking，不跨 Section 混合内容。
- 每个 Chunk 保留 Paper、Version、Section、Page、Block、Element 溯源。
- Structure Version 或 Chunking Version 变化时，只重建受影响阶段及其下游数据。
- 批量生成 Paper、Section、Chunk 三层 Embedding。
- 使用 pgvector HNSW 执行 Cosine Vector Search。
- 使用 PostgreSQL `tsvector`、GIN 和 BM25 执行 Sparse Retrieval。
- 使用 Project/Paper/Version/Section Scope 与 Metadata Filter 缩小搜索范围。
- 融合 Dense 与 Sparse Candidate，并执行 Rerank、Threshold 和去重。
- 返回完整可追溯 Evidence；没有足够证据时返回 `no_evidence`。
- 使用 Query Rewrite/Multi-query 提高用户表达与论文原文之间的召回。
- 在命中 Chunk 周围执行同 Section Neighbor Expansion，并通过 Evidence Judge 再过滤。
- 使用 `read_paper` 按 Section、Page、Element 精确阅读。
- 运行可恢复 Agent Tool Loop，由模型选择 Search 或 Read。
- 按 Token Budget 和每篇论文配额构建平衡 Context。
- 校验 `[E{数字}]`（检索证据）与 `[P{数字}]`（阅读段落）引用并附加 Paper/Section/Page 来源。
- 使用 Redis 保存短期 Session、Agent Checkpoint、Active Chunk 和 Tool Result。
- Agent 自动将 Interaction 保存到 PostgreSQL；Notes 和长期 Preference 当前提供 Domain/Schema/Repository 基础，尚无面向用户的 CLI/Tool/API。
- 可选使用 OpenAI 批量 Embedding 和 Sentence Transformers Cross-Encoder。
- 将 PaperProfile 的稳定字段保存为可查询行，并为每个字段保存 EvidenceLink。
- 保存版本化 Claim、规范化 ResearchEntity、Alias 和 Paper/Entity Relation。
- 使用 Claim–Evidence Judge 阻止未通过验证的 Claim 进入 verified。
- 使用 `profile-extract` 完全离线生成 Research Graph 数据。
- 使用 `compare` 或 Agent `compare_papers` 返回结构化、逐 Cell 带证据的多论文比较。
- Profile/Claim/Entity/Relation 的所有 Repository 查询强制使用 Project Scope。

## 2. 环境要求

必须安装：

- Python 3.12 或更高版本。
- `uv`。
- PostgreSQL。
- PostgreSQL 的 `pgvector` 扩展。

默认 PDF Parser 是 PyMuPDF，它会由项目依赖自动安装。

Poppler 是可选后备方案。若需要使用 Poppler，系统中必须存在：

```bash
pdftotext
pdfinfo
```

可以用以下命令检查：

```bash
command -v pdftotext
command -v pdfinfo
```

macOS Homebrew 环境安装 pgvector：

```bash
brew install pgvector
```

当前版本必须使用 PostgreSQL，不能直接改用 SQLite。

## 8. Ingestion 输出

导入完成后，CLI 会输出 JSON 汇总：

```json
{
  "run_id": "...",
  "scanned": 100,
  "missing": 1,
  "counts": {
    "new": 3,
    "modified": 1,
    "duplicate": 2,
    "unchanged": 94,
    "missing": 1,
    "failed": 0
  },
  "failed": []
}
```

各状态含义：

| 状态 | 含义 |
|---|---|
| `new` | 新路径且新的 PDF 二进制内容 |
| `modified` | 已知路径的文件内容发生变化 |
| `duplicate` | SHA-256 相同，或正文 Content Hash 相同 |
| `unchanged` | 路径和文件内容均未变化 |
| `missing` | 全项目扫描时发现已知路径不再存在 |
| `failed` | 当前文件在 Hash、Metadata、Identity、Parsing、Structure、Chunking、Embedding 或 Indexing 阶段失败 |

如果任意文件失败，CLI 返回非零退出码，并在 `failed` 数组中给出：

```text
path
error_code
error
```

其他论文仍会继续处理。

## 10. 本地生成文件

项目初始化和导入后，会生成：

```text
.paper-agent/
├── project.json
└── parsed/
    └── {paper_id}/
        └── {version_id}/
            ├── document.json
            ├── document.md
            └── assets/
```

### `project.json`

保存当前目录稳定的 `project_id`。不要随意删除，否则重新初始化可能产生新的项目身份。

### `document.json`

机器可读的 Canonical Parsed Document，包含：

- Paper、Version、Source File ID。
- Parser 名称与版本。
- Canonical Schema Version。
- Page 尺寸和页码。
- 文本 Block。
- BBox。
- Reading Order。
- 基础 Block Type。

### `document.md`

面向人和后续 LLM 处理的可读 Markdown，并保留页码来源标记：

```markdown
<!-- page: 1 -->
```

### `assets/`

为后续 Figure、Table、Equation 和 Algorithm 二进制资源导出预留。Phase 1C 已在 PostgreSQL 保存基础 Element 记录与 Block/BBox 溯源，但尚未完成图片裁切、表格单元格恢复或公式 LaTeX OCR。

## 11. Phase 1C 结构化数据

执行 `ingest` 后，单篇论文的逻辑处理链为：

```text
Canonical Parsed Document
→ Heading 层级恢复
→ Section Tree + Block 归属
→ Figure/Table/Equation/Algorithm Element
→ Semantic Block / Dependency Group
→ Section-aware Semantic Chunk
→ PostgreSQL 派生数据与版本状态
```

Phase 1C 新增的 PostgreSQL 表：

| 表 | 用途 |
|---|---|
| `sections` | Section Tree、父子关系、页范围和 Block 归属 |
| `elements` | Figure/Table/Equation/Algorithm 基础模型 |
| `semantic_groups` | 普通语义块与不可随意拆散的 Element Dependency Group |
| `chunks` | Section-aware Chunk 及完整溯源 |
| `derived_data_states` | Parsed Document Hash、Structure Version、Chunking Version 与恢复状态 |

Chunk 的溯源字段包括：

```text
paper_id
version_id
section_id + section_path
page_start + page_end
source_group_ids_json
source_block_ids_json
related_element_ids_json
chunking_version
```

可以直接用 SQL 检查最近生成的 Chunk：

```sql
SELECT
  chunk_order,
  section_path,
  page_start,
  page_end,
  chunk_type,
  token_count,
  source_block_ids_json,
  related_element_ids_json
FROM chunks
ORDER BY version_id, chunk_order
LIMIT 20;
```

检查 Section Tree：

```sql
SELECT
  section_order,
  level,
  section_path,
  page_start,
  page_end,
  source_block_ids_json
FROM sections
ORDER BY version_id, section_order;
```

### 阶段恢复规则

每次导入都会比较四组相互独立的版本：

```text
Parser + Canonical Schema Version
Structure Version
Chunking Version
Canonical Parsed Document Hash
Embedding Provider / Model / Version / Dimension
Hierarchical Index Version
```

- 所有版本都未变化：直接复用已完成的 `indexed` 状态。
- 只有 Chunking Version 变化：读取已有 Section/Element/Group，只重建 Chunk。
- Structure Version 变化：读取已有 Canonical Document，重建结构与 Chunk，不重新解析 PDF。
- Parser 或 Canonical Schema Version 变化：重新解析，并重建全部下游派生数据。
- Structure 是否可复用同时要求 `document_hash` 与当前 Parser/Schema 对应的最新 Parsed Document 一致；存量 `NULL` 一律按非当前处理。
- 只有 Embedding 或 Index Version 变化：复用已有 Chunk，只重建 Paper/Section/Chunk Index。
- 使用 `--force-reindex`：从 Metadata/Parsing 开始强制重建当前结果。

## 12. Phase 2A 索引与检索

执行 `ingest` 后，默认流水线会继续处理到 `indexed`：

```text
Chunked PaperVersion
→ 构造 Paper / Section / Chunk Index Document
→ 256 维批量 Embedding
→ pgvector HNSW Index
→ PostgreSQL tsvector / GIN
→ Index State = indexed
```

Phase 2A 新增的 PostgreSQL 表：

| 表 | 用途 |
|---|---|
| `embedding_configs` | Provider、Model、Version 和 Dimension |
| `indexing_states` | 每个 Project/PaperVersion 当前索引状态及源数据摘要 |
| `paper_embeddings` | Paper-level Vector |
| `section_embeddings` | Section-level Vector |
| `chunk_embeddings` | Chunk-level Vector |

同时为以下表增加 `search_vector` 生成列和 GIN 索引：

```text
papers
sections
chunks
```

### 默认 Embedding Provider

默认使用：

```text
provider = paper-agent
model = feature-hashing-256
version = hashing-v1
dimension = 256
```

这是一个离线、确定性、无需模型下载的基线 Provider，适合本地运行、开发测试和专有词检索。它不是神经语义模型；生产场景可以实现同一个 `EmbeddingProvider` 接口，替换为本地 Sentence Transformer 或远程 Embedding API，但当前 pgvector Schema 要求输出维度为 256。更换维度需要配套 Migration。

### 调用 search_knowledge

直接使用 CLI：

```bash
uv run paper-agent search \
  --root /path/to/research-project \
  --max-evidence 5 \
  'SCANet 的 codebook 是如何构建的？'
```

也可以通过内部 Python Service 调用：

```python
import os
from pathlib import Path

from paper_agent.application import build_search_knowledge_service
from paper_agent.domain.retrieval import MetadataFilter, SearchRequest, SearchScope
from paper_agent.project_manifest import ProjectManifestStore

root = Path("/path/to/research-project").resolve()
project = ProjectManifestStore(root).load()
database_url = os.environ["PAPER_AGENT_DATABASE_URL"]

search = build_search_knowledge_service(database_url=database_url)
result = search.search_knowledge(
    SearchRequest(
        query="SCANet 的 codebook 是如何构建的？",
        scope=SearchScope(project_id=project.project_id),
        filters=MetadataFilter(
            year_from=2020,
            venues=("CVPR", "ICCV"),
        ),
        max_evidence=5,
    )
)

print(result.status.value)
print(result.has_sufficient_evidence)
for evidence in result.evidence:
    print(evidence.paper_title)
    print(evidence.section_path, evidence.page_start, evidence.page_end)
    print(evidence.text)
    print(evidence.relevance)
```

### Scope 与 Metadata Filter

可以显式限定检索范围：

```python
scope = SearchScope(
    project_id=project.project_id,
    paper_ids=(paper_id,),
    version_ids=(version_id,),
    section_ids=(section_id,),
)
```

Metadata Filter 支持：

```text
year_from / year_to
venues
authors
chunk_types
```

所有检索都强制保留 `project_id` Scope，防止不同项目的论文数据互相泄漏。

### 检索流程

```text
Query
→ Explicit Scope / Metadata Resolution
→ Paper Dense Retrieval
→ Section Dense Retrieval
→ Chunk pgvector Dense Retrieval
  + PostgreSQL FTS Candidate / BM25
→ Dense + Sparse Fusion
→ Reranker
→ Relevance Threshold
→ Near-duplicate Removal / Paper Quota
→ Evidence 或 no_evidence
```

最终 Evidence 至少包含：

```text
paper_id / version_id / paper_title
section_id / section_path
page_start / page_end
chunk_id / element_ids
text / relevance
dense_score / bm25_score / rerank_score
```

不同 Score 的量纲不同，不应直接把 `dense_score`、`bm25_score` 和 `rerank_score` 机械比较。最终是否返回 Evidence 以经过校准的 `relevance` 和 Threshold 为准。

如果所有候选均低于阈值，结果会明确返回：

```text
status = no_evidence
has_sufficient_evidence = false
evidence = ()
```

## 13. Phase 3 Agent、Read 与模型配置

### 13.1 什么时候需要 API Key

以下操作不需要 API Key：

```text
init / ingest / status / search / read
默认 Hashing Embedding
默认 Lexical Reranker
全部离线单元测试和 Fake Model Agent 测试
```

执行 `ask` 时需要模型 Key。以 OpenAI Provider 为例：

```bash
export PAPER_AGENT_LLM_PROVIDER='openai'
export OPENAI_API_KEY='你的-key'
export PAPER_AGENT_LLM_MODEL='你账户可用的模型名'
```

使用 Xiaomi MiMo：

```bash
export PAPER_AGENT_LLM_PROVIDER='mimo'
export PAPER_AGENT_LLM_MODEL='mimo-v2.5-pro'
export MIMO_API_KEY='你的真实-MiMo-Key'
export MIMO_BASE_URL='https://api.xiaomimimo.com/v1'
```

MiMo Provider 使用独立的 Key 和 Base URL，不需要把 MiMo 配置映射到
`OPENAI_API_KEY` 或 `OPENAI_BASE_URL`。按量付费与 Token Plan 的 Key、Base URL
不能混用；Token Plan 用户应使用套餐页给出的专属 Base URL。

OpenAI Provider 使用 `previous_response_id` 继续工具循环；MiMo 当前不支持该字段，
因此 Paper Agent 会把模型输出项、Function Call 和 Function Call Output 保存进
Redis Checkpoint，并在续轮中重传完整历史。得到充分检索证据或有效 Read 结果后，
最终生成请求不再暴露工具，也不再携带容易诱导模型继续调用工具的 Function Call
协议历史；系统会将 Tool Result 整理为有界的纯文本证据包，单独执行答案合成。
最终请求会显式列出工具返回的可用 `[E编号]`；如果 MiMo 第一次生成遗漏引用，
或把新 Tool Call 写成普通文本，Provider 会把这份无效输出连同纠正指令反馈给模型，
并在不重复执行检索工具的情况下自动严格重试一次。

不要把真实 Key 写入 Git。可以复制 `.env.example` 为 `.env`，填值后在当前 Shell 显式加载：

```bash
set -a
source .env
set +a
```

```bash
  --version-id VERSION_ID
```

该命令读取已经生成的 Section-aware Chunk，使用默认 Rule-based Extractor 批量生成 Profile、Claim、显式命名 Entity 和 Relation。它不访问网络，也不逐 Chunk 调用 LLM。输出包含 Profile/Field ID、Evidence ID、Extractor/Schema Version 和各类记录数量。

至少两篇论文完成 Profile 提取后执行：

```bash
uv run paper-agent compare \
  --root /path/to/research-project \
  PAPER_ID_A PAPER_ID_B PAPER_ID_C
```

输出是结构化 JSON，并在 `derivation` 中记录确定性算法、Generator Version、Schema Version，以及空的 Model/Prompt（默认路径未使用 LLM）。维度包括：

```text
research_problem
assumptions
method
datasets
metrics
experimental_setting
results
advantages
limitations
```

每个 Cell 返回 `evidence_backed` 或 `insufficient_evidence`。`evidence_backed` Cell 包含 normalized value、原始描述、Confidence、Review Status 和 EvidenceLink；`insufficient_evidence` Cell 的值为空，并带 `no_evidence` 原因。某个维度至少需要两篇论文存在证据才标记为 directly comparable。

Agent Runtime 同时暴露 `compare_papers` Tool。Tool 返回相同的 Dimension/Cell 结构，并把比较证据汇总到顶层 `evidence`，使用稳定的 `[E编号]` 供最终答案引用校验。

Research Graph 新增表：

| 表 | 用途 |
|---|---|
| `paper_profiles` | 特定 Project/PaperVersion 的 Profile 生成谱系和 active/superseded 状态 |
| `paper_profile_fields` | 可查询的稳定 Profile 字段、多值顺序、置信度和审阅状态 |
| `claims` | Claim、极性、生成版本、Review 与 Entailment 状态 |
| `research_entities` | 项目内规范化研究实体 |
| `research_entity_aliases` | Entity Alias 和规范化反查 |
| `paper_relations` | Paper/Entity 类型化关系、方向、去重 Key 和生成谱系 |
| `evidence_links` | 目标到 Paper/Version/Section/Chunk/Page/Block/文本快照的证据链接 |

所有读取和写入都以 `project_id` 验证 PaperVersion 或 Entity 归属。历史 Evidence 的 Section/Chunk/Element ID 作为快照标识保存，不使用会在结构重建时级联删除的外键；Paper/Version 和证据文本仍保留完整血缘。


### 13.8 Retrieve + Offload + Delegate：Artifact 与受控多 Agent 委派

分级执行策略：

| 请求类型 | 策略 |
|---|---|
| 普通论文问答 | Retrieve（检索/阅读/比较走主 Agent） |
| 长上下文、多论文比较 | Retrieve + Offload（完整 Tool 结果写入 Artifact，模型只收紧凑摘要） |
| 系统文献调研、跨领域探索 | Retrieve + Offload + Delegate（隔离 Worker 并行执行研究子问题） |

#### Artifact 落盘与读取

完整 Tool 结果（比较矩阵、整章段落、全部检索候选）写入：

```text
.paper-agent/artifacts/blobs/sha256/<ab>/<full-sha256>.json.gz
.paper-agent/artifacts/manifests/<artifact-id>.json
```

Blob 采用 SHA-256 内容寻址、gzip 压缩、临时文件 + 原子重命名；读取时重新校验哈希。Catalog 元数据保存在 PostgreSQL `research_artifacts`，引用清单保存在 `artifact_citations`。所有读取强制 `project_id` 隔离。

模型只收到：

- 紧凑 `model_payload`（默认单结果 ≤ 2000 tokens，单轮累计 ≤ 6000 tokens）
- `artifact_ref`（artifact_id + 可用视图）
- `citation_manifest`（供最终答案引用校验，不需要读 Blob）

需要更多细节时，主 Agent 调用 `read_artifact`（参数 `artifact_id`/`view`/`cursor`/`max_tokens`，`max_tokens` 上限 4000，project_id 由 Adapter 绑定）或 `search_artifact`。

#### 委派（第一版：同步、单层、受控）

主 Agent 调用 `delegate_research`（objective、paper_ids、requested_workstreams、max_workers），随后调用 `collect_research_task` 汇总。Worker 永远只收到任务简报（目标、论文 ID、输入 Artifact、允许的工具、输出 Schema、预算），绝不接收主对话历史；Worker 结果经 Schema 校验后作为 Worker Artifact 保存，主 Agent 只收到摘要 + artifact_ref + citations。

已实现的 Worker：

| Worker | 状态 | 允许的工具 |
|---|---|---|
| paper_analyzer | 可用 | search_knowledge, read_paper, read_artifact |
| evidence_verifier | 可用 | read_artifact, read_paper（verdict 只能是 supported/contradicted/insufficient/unreviewed） |
| landscape_scout / relation_analyst / contradiction_finder / cross_domain_analogy_scout | 已注册、未实现（Scheduler 会明确拒绝） | — |

CLI 直通（需要 LLM API Key）：

```bash
uv run paper-agent delegate \
  --root /path/to/research-project \
  --paper-id PAPER_ID_A --paper-id PAPER_ID_B \
  --workstream method --workstream verification \
  '比较这两篇论文的方法与验证证据'
```

新增表：

| 表 | 用途 |
|---|---|
| `research_artifacts` | Artifact 目录：类型、Schema 版本、内容哈希、存储后端、Token 估计、状态、过期时间 |
| `artifact_citations` | Citation Manifest 持久化，Finalizer 只凭清单校验引用 |
| `research_tasks` | ResearchTask：问题、类型、计划、预算、状态 |
| `work_units` | WorkUnit：目标、论文/Artifact 输入、Worker、Schema、预算、幂等 Generation Key、状态 |

限制：最大并行 Worker 3～5（第一版同步顺序执行）、委派深度 1（Worker 不能创建 Worker）、WorkUnit 最多自动重试一次、Worker 只写 Staging Artifact、canonical Research Graph 只能由验证服务写入。

## 14. 增量处理和去重规则

处理顺序如下：

```text
文件路径
→ 文件大小与 mtime
→ SHA-256
→ PDF Metadata
→ 规范化正文 Content Hash
→ DOI / arXiv ID
→ Normalized Title + Authors
→ Paper / Version
```

### 相同 PDF 改名

如果 PDF bytes 完全相同：

```text
SHA-256 相同
→ 复用已有 File/Paper/Version
→ 不重新 Parse
```

### PDF 二进制不同但正文相同

例如 PDF metadata、压缩方式或下载来源不同：

```text
file_hash 不同
content_hash 相同
→ 保留两个 File
→ 复用同一 PaperVersion 和 Parsed Document
```

### 同一论文的不同版本

如果 DOI 或 arXiv Identity 相同，但正文 Content Hash 不同：

```text
同一 Paper
→ 创建新的 PaperVersion
→ 分别保存 Parsed Document
```

系统不会只依赖一个模糊标题自动合并论文。标题匹配必须同时具有规范化作者信息，避免错误合并。

## 15. 删除和移动文件

只有在未指定局部扫描路径、即执行完整项目扫描时，系统才会判断哪些已知路径已经消失：

```bash
uv run paper-agent ingest --root /path/to/research-project
```

局部扫描不会把扫描范围之外的论文标记为 `missing`。

`missing` 只表示文件路径当前不在磁盘上，不会删除数据库中的 Paper、Version、File 或 Parsed Document。

## 16. 常见错误

### PostgreSQL 连接被拒绝

```text
connection refused
```

检查：

- PostgreSQL 服务是否启动。
- 端口是否为 `5432`。
- 数据库和用户是否存在。
- `PAPER_AGENT_DATABASE_URL` 是否正确。
- PostgreSQL 是否允许当前地址连接。

### Redis 提示 Authentication required

在 `PAPER_AGENT_REDIS_URL` 中加入密码，例如：

```bash
export PAPER_AGENT_REDIS_URL='redis://:你的密码@localhost:6379/0'
```

### 未设置数据库连接

```text
Set PAPER_AGENT_DATABASE_URL or pass --database-url
```

设置环境变量，或在命令中使用：

```bash
--database-url 'postgresql+psycopg://...'
```

### PyMuPDF 不可用

重新同步依赖：

```bash
uv sync --extra dev
```

或者安装 Poppler 并使用：

```bash
--parser poppler
```

### 加密 PDF

密码保护的 PDF 会返回：

```text
encrypted_pdf
```

当前版本不接收 PDF 密码。需要先在授权范围内解密文件，再重新导入。

### 损坏或没有可读页面的 PDF

可能返回：

```text
parse_failed
empty_pdf
```

失败只影响当前 PDF，可以修复或替换文件后再次执行 Ingestion。

### 结构或分块失败

可能返回：

```text
structure_failed
chunk_failed
```

失败记录会保留在 Ingestion Item 中。修复输入或算法后重新执行 `ingest`；如果版本号未变但希望强制重建，使用 `--force-reindex`。

### PostgreSQL 找不到 vector Extension

如果 Migration 输出：

```text
extension "vector" is not available
```

先安装 pgvector：

```bash
brew install pgvector
```

如果输出：

```text
permission denied to create extension "vector"
```

说明当前应用用户不是数据库管理员。使用管理员账号在目标数据库执行一次：

```bash
psql -U chenyuan -d paper_agent -c 'CREATE EXTENSION IF NOT EXISTS vector;'
```

然后继续使用 `paper_agent` 应用用户执行 `db-upgrade`。

### Embedding 或索引失败

可能返回：

```text
embedding_failed
index_failed
```

检查 pgvector Extension、Migration、Embedding Dimension 和数据库连接。默认 Schema 只接受 256 维向量。修复后再次执行 `ingest`；系统会复用已有 Parsed Document 和 Chunk，从索引阶段恢复。

### 文件在 Hash 过程中被修改

会返回：

```text
file_changed_during_read
```

等待文件复制、同步或下载完成后重新执行即可。

## 18. 当前能力边界

当前版本可以完成：

```text
真实 PDF 目录
→ 增量扫描
→ 二进制和正文去重
→ Metadata Extraction
→ Paper/Version Identity
→ PDF Layout/Text Parsing
→ Canonical Parsed Document
→ Section Tree / Element / Dependency Group
→ Section-aware Semantic Chunk
→ Paper / Section / Chunk Embedding
→ pgvector HNSW + PostgreSQL FTS/BM25
→ Metadata-scoped Hierarchical Hybrid Retrieval
→ Traceable Evidence / no_evidence
→ Query Rewrite / Multi-query / Neighbor Expansion / Evidence Judge
→ search_knowledge / read_paper Tool
→ Recoverable Agent Loop
→ Token-budgeted Context / Citation Validation / Final Answer
→ Redis Session + PostgreSQL Interaction/Note/Preference Memory
→ PaperProfile / Claim / ResearchEntity / PaperRelation / EvidenceLink
→ 离线 Profile Extraction
→ Evidence-backed Structured Comparison / insufficient_evidence
→ PostgreSQL + Local FS 持久化
```

当前版本不能完成：

- ComparisonTask/Dimension/Cell/SynthesisArtifact 的历史比较持久化和人工修订；当前比较结果由已持久化 Profile/Claim 确定性构建。
- 可恢复 Literature Review Workflow、Screening Decision、Evidence Matrix、Research Gap 和报告快照。
- 机制级跨领域迁移、Assumption Compatibility、IdeaCard 和 Novelty Check。
- 外部 DOI/arXiv/BibTeX/RIS Provider、引用发现、Zotero 同步和新论文提醒。
- Figure、Table、Equation、Algorithm 的精细视觉/结构恢复与资源导出。
- Figure/Table 的精细结构恢复、图片裁切、表格单元格和公式 LaTeX OCR。
- 面向用户的 Web/API 服务、鉴权、多租户隔离和并发任务队列。
- Interaction/Note 的向量索引与真正的长期语义召回；当前是 PostgreSQL 结构化/关键词检索基础。
- Query Rewrite/Evidence Judge 的在线模型实现；当前默认实现强调可离线、保守和低成本。
- 神经 Provider 的自动质量校准、模型缓存管理和生产级观测。
- Citation 与原 PDF 可视区域的深链接和高亮预览。

下一阶段最合理的纵切是持久化 Evidence-backed Comparison：新增 ComparisonTask/Dimension/Cell/SynthesisArtifact、输入 PaperVersion 快照、人工 Cell 修订和增量刷新。随后再进入 Literature Review Workflow；服务化、队列、认证、可观测性、Element 精细解析和系统评测按 `research-graph-roadmap.md` 的 Phase E/F 推进。
